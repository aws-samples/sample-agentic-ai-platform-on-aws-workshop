Seeing the platform run Explain · 10 min

The dashboard combines four evidence sources:

  1. AgentCore metrics: invocations, errors and latency.
  2. Policy decisions: allowed and denied tool calls.
  3. Online evaluation: quality scores.
  4. Model-gateway spend logs: spend per key, read through the gateway's API rather than from CloudWatch.

This workshop. Transaction Search is enabled by the foundation. Overview reads the first three sources as CloudWatch metrics and the fourth from the model gateway's spend logs through its API; nothing on it comes from CloudWatch Logs. Open CloudWatch for a conversation's traces.

CloudWatch Omni is another front end over the same data. It is listed as an option, but not set up today.

For changes, read two audit records:

  • Platform releases: who created, submitted, approved and promoted.
  • CloudTrail: which AWS API changed a resource, under which identity.

A trace ID correlates requests; it does not identify the user. Sampled traces miss some usage, so spend comes from model-gateway logs that see every call.

Production path. Alarm on errors, latency, budget burn and quality. Give every alarm a notification target and no-data rule. A heartbeat distinguishes idle traffic from a broken pipeline.

7.2How is quality watched in Prod?

OptionProsConsChoose when
Online evaluation: a sampling rate, evaluators, a quiet timeoutcontinuousjudge cost; results minutes lateralways

User feedback onlyfreesparse and biasednever alone

This workshop. Promotion registers three online settings:

  • Sampling: 100% of Prod conversations.
  • Judges: Helpfulness, Harmfulness and ToolSelectionAccuracy. AgentCore names its built-in judges with a Builtin. prefix, so workshop apply 7 echoes the registered configuration as Builtin.ToolSelectionAccuracy and CloudWatch uses that as the metric name; workshop scores and the Overview drop the prefix.
  • Quiet timeout: one minute; scores arrive about 8–11 minutes after traffic.

Feedback is tied to sessions. Rollback means putting the previous configuration back in Prod. Today that is a new release of the previous blueprint version through the same gate, approval and promotion; the UI has no rollback button yet.

Production path. Roll back on quality regression and turn user feedback into new dataset tests.

7.3What may telemetry keep, and who may read it?

OptionProsConsChoose when
Full content: prompts, answers and tool arguments in every tracethe richest debugging and evaluation detailpersonal data lands in the trace store; every reader sees everything; retention becomes a data decisionsynthetic data; Dev; a workshop

Redact at capture: content kept, named fields removed before exportdebugging detail without the namesredaction rules to maintain; collector filters and log masking are extra layers, not substitutesproduction, with a data owner's approval

This workshop. Full traces use synthetic HR data. CloudWatch IAM permissions control trace access, independently of platform personas. Online judges read the same stored content.

Production path. Start with metadata only. Keep redacted content when the data owner approves it; judge-based evaluation needs content. Define readers and retention per source. Tenant trace access is a data boundary.

Filtering and redaction happen at different points:

  • Before export: ADOT's AWS_REDACT_SPAN_ATTRIBUTES names attributes to blank.
  • After storage: reader filters select rows; they do not redact fields.

AWS_GENAI_CONTENT_EXTRACTION_OPT_OUT=true still keeps prompts and answers on spans. It is not a privacy opt-out.

7.4How is shared cost allocated?

OptionProsConsChoose when
Measured consumption: every call priced and charged to the key that made itallocation follows useneeds complete, non-overlapping metering and a pricing basis; the foundation stays unallocatedmetering exists, as here through the model gateway
Usage-based share: shared cost split by a proxy such as request countrepeatable when direct attribution is missinga request count under-charges large or slow requestsshared services without per-call metering
Platform-funded pool: the foundation paid centrally; teams see only their direct spendsimple for teamsunit costs hide the shared spend; nobody feels the platform's billa first platform, few workloads

This workshop. Costs have two categories:

  • Model calls: measured per key, identifying agent, environment and model.
  • Shared services: network, gateways, registry and proxy are platform-funded; the Keycloak stand-in from module 2 is unallocated too, though in production the company's identity provider is its own cost centre, not the platform's.

The rough fixed-cost estimate is 0.28 USD/hour: proxy/database ~0.10 plus nine interface endpoints ~0.18. The corporate IdP from module 2 adds about 0.08 USD/hour (one Fargate task and an internal load balancer; its two HTTP APIs cost almost nothing at this traffic), about 0.36 USD/hour in total while everything is deployed. This is not the full platform bill. Endpoints are billed per AZ-hour, including idle time. For HR, use key spend ÷ answered conversations; failed and retried calls remain in spend.

Production path. Make cost accounting explicit:

  • Allocation: document the shared-cost rule and revisit it as traffic and tenants change.
  • Evidence: activate billing tags; trace attributes are not billing tags. Reconcile gateway estimates with Cost Explorer or CUR.
  • Control: AWS Budgets sends delayed alerts; gateway caps block calls. Read unit cost alongside quality.

Hands-on 20 min

Watch it run, then write the production path
  1. commandworkshop apply 7. It needs the Prod agent that module 6's promotion created: without an approved and promoted release it stops with no Prod agent yet. It first prints the online evaluation that promotion registered (status, sampling, quiet timeout, evaluator ids), then sends ten Prod conversations by default (prod_traffic in your record, a whole number from 1 to 50), three at a time with one line per conversation, and reports OK 10 of 10 conversations answered. It then waits, up to three minutes, for those invocations to show in the Prod metrics and prints invocations, errors, sessions and latency, the policy allow and deny counts, and the team's spend by environment. It posts one thumbs-up for the first answered conversation (POST /feedback), reads the long-term memory records of employee E1001, the sample conversation workshop apply 6 wrote into the Dev memory, and ends with the online scores so far (or none yet: workshop scores shows them when they arrive) and two links, Overview and CloudWatch GenAI observability. The step usually takes about a minute (ten conversations were answered in 31 s on warm sessions); a cold session takes 25 to 40 s and the metrics check can wait up to three minutes, so allow up to five.
  2. screenOverview, with Prod selected: read invocation counts, error rate and latency, spend by environment, policy Allow/Deny counts, the online scores so far and the feedback counts; the thumbs-up apply 7 posted is already there.
  3. screenCalculate Prod key spend ÷ Prod conversations answered. The apply output counts only the conversations it just sent (ten by default). The Prod key has also paid for module 6's seeded traffic (the answered count workshop traffic --prod 3 printed, normally three) and for any Prod question you asked after promotion in Playground · Prod or with workshop ask --env prod, so add those to the denominator. Failed calls add spend, not successful outcomes.
  4. screenCloudWatch · GenAI observability: follow one Prod trace step by step.
  5. commandworkshop scores: read the online scores. The three conversations module 6 seeded with workshop traffic --prod 3 should already be scored; today's ten arrive 8 to 11 minutes after each session goes quiet. The command lists the mean and the sample count per evaluator over the last three hours, then the platform's own view of the same numbers; the Overview shows them too. workshop traffic --prod 3 sends more conversations whenever you want fresh scores.
  6. recordFill design-record.yaml's backlog: one production action and owner per recap row.
Remember. Watch quality alongside cost. Price the successful outcome, including failed attempts. Your completed design record and backlog form the production plan.

Glossary

Trace, span
A trace records one request (one turn); spans record its individual steps.
Session
One conversation under one session id, kept until you start a new session in the Playground or pass a new one to workshop ask --session; each turn of it is a trace.
Transaction Search
CloudWatch search over spans, including agent conversations.
Online evaluation
Quality scoring over real agent traffic.
Sampling
The fraction of conversations recorded or evaluated.
Quiet timeout
Idle interval used to decide that a conversation has ended.
Feedback
A rating and comment tied to a session.
Rollback
Promote the previous blueprint version again; Prod's DEFAULT endpoint follows the new harness version.
Audit trail
Release records identify platform changes; CloudTrail records AWS API activity. Event history keeps 90 days of management events; data events require configuration. These are not prompt records.
Redaction
Remove sensitive fields before telemetry is stored or exported.
Retention
How long telemetry is kept.
Unit cost
Spend divided by successful business outcomes. Failed attempts remain in the spend.
Cost allocation
Assign direct and shared costs to the teams that use the platform.
Hardening
Replace workshop shortcuts with production settings.
