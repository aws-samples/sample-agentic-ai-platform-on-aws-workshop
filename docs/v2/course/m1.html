What this module decides

Northstar, or the organisation you bring, has more teams building agents than its shared practices can support. This module turns that pressure into a design, one decision at a time: name the scaling problem, write requirements a reviewer can test, decide who owns what, place accounts and tenants, lay the landing zone and its telemetry, and finally review the complete target architecture those decisions point to. Each step answers a question the previous one raised. The output is a requirements brief, a persona and responsibility record, an account, tenant and telemetry boundary map, and a reviewed request flow that guide Module 2.

Role: platform architect. Points: 30 (requirements 10; architecture 20). This is a design module and needs no deployed resources; bring the success statement and journey record from setup, and use an anonymised customer context or the fictional Northstar example.

Keep these decisions separate. A central team can operate workloads in several accounts; domain teams can practise federated responsibilities within one account; an ISV customer tenant may contain many users and workloads. Neither "federated" nor "one tenant" answers them all.

Recognise the scaling problem 5 min

Start with what is going wrong today, not with services. A platform is useful when it removes repeated work or supplies a control that individual teams cannot sustain, so the first decision is which capability or control should become shared, judged by the observed failures it would remove. The table lists the usual symptoms; you will pick two, the boundary sharing must preserve, and a result for each that a reviewer could observe.

ChallengeSymptomPlatform response to consider
Agent sprawlTeams rebuild similar agents without knowing what existsDiscoverable owners, versions, reusable tools and maintained blueprints
Shadow AIA deployed agent has no approved identity or release recordAn accessible onboarding path with enforceable access and release controls
Cost blindnessA bill increases but no owner can attribute the activityWorkload usage records and a defined basis for cost allocation
Observability gapA request ID cannot connect runtime and tool failuresCorrelated telemetry with authorised operator access
Integration chaosEvery team implements and patches the same connectionA versioned tool interface, credential handling and an onboarding contract
Ownership ambiguityA failed agent has no named maintainer or incident responderExplicit delivery, business acceptance and support responsibilities

Worked example: Northstar

Northstar's Service and Sales teams each maintain a connector to the same customer-record system. A permission fix must be implemented twice. When a request fails between an agent and the connector, neither team can identify the responsible component from the request ID.

Employees use agents through an existing staff portal. Service has engineers and an on-call rotation; Sales supplies domain experts but has no engineering team. A small central team can operate shared services. Each business unit must retain access only to its permitted records. These are exercise assumptions, not customer findings.

Northstar can prioritise integration chaos and ownership ambiguity: the duplicated fix and unresolved failure are concrete evidence. Tenant isolation remains a required boundary even if it is not the first productivity improvement.

A shared connector reduces duplicate maintenance, but its owner must manage compatibility and availability for both teams. Share the interface and onboarding process while preserving each caller's permissions. If the teams need incompatible data policies, a common contract with separate tool instances may fit better.

The enterprise platform sample's platform interface shows how use cases depend on published configuration and authentication interfaces. A catalogue adds a separate discovery and publication concern: an endpoint configuration record alone is not an approved asset catalogue.

Write a testable requirement 5 min

Turn each priority into a requirement someone can accept or reject: who needs a capability, the boundary it preserves and an observable check, written before any implementation is chosen. The result is a short requirements brief with acceptance criteria, owners, assumptions and the questions that could change the design.

"Use a gateway" names an implementation. "A second team can use an approved tool without copying its connector or receiving another team's credentials" explains the capability and why it matters. Gateway choices follow in Module 2.

Capture the context that changes a design

Identify platform users and agent consumers separately. At Northstar, engineers and reviewers use the platform; employees consume agents in the staff portal. In an ISV scenario, identify the customer administrators, builders and consumers of the product. Record the channel owner and which actions each role may perform; the next section turns these into personas.

Record engineering and support capacity for each team. "Service can develop and operate its workloads; Sales provides domain acceptance but needs engineering support" is enough to inform the operating model. Organisation size alone does not establish those responsibilities.

Add non-functional constraints when they matter: permitted processing locations, data classification, retention and deletion, response time, expected concurrency, usage attribution and recovery. Give each a measurement context. A latency target needs a request type, workload size, concurrency, measurement window and threshold. An unknown retention period needs a data owner and a decision date.

Accounts, tenants and ownership: three decisions, not one 5 min

The operating model says who runs what. It does not say where resources run or whose data must stay apart, and the open question in your brief, who may approve cross-unit access, is exactly that kind of question. Make the account, tenant and ownership decisions separately, then trace a trusted identity through every boundary. The result is a resource-placement map and a tenant access contract, with the checks later labs must pass.

Account placement limits where resources and administrative permissions live. Tenant isolation decides whose data and actions a request may reach. Administrative ownership decides who may change a resource. Several tenants can share an account, one tenant can span several accounts, and a central team can administer resources in accounts it does not own.

Keep two related questions separate from ownership and account placement:

  • Tenant boundaries: whose data, credentials, actions and records must stay separate, and what enforces that separation? This page introduces it in D1.4 and the tenant layers below; D2.13 builds it into the control plane. Tenants can share or span accounts; tenancy does not determine who runs the platform.
  • Platform usage: who uses the platform, and through which business channel or interface? This workshop uses the platform's Playground and API, introduced in Module 4; the architecture review at the end of this page follows these paths through the reference platform.

Define the tenant before selecting controls

A tenant is the business unit or customer whose permissions, credentials, data and usage must be bounded. In Northstar, Service and Sales are the proposed tenants; in this workshop they are People Operations and Finance Operations. In an ISV product, a customer organisation may be a tenant containing many users and workloads.

Write how a verified caller maps to a permitted tenant and role. If a user belongs to more than one tenant, the server validates the requested tenant against that membership. A tenant name in a prompt, URL or request body is not proof of membership. Agents that derive a memory actor id from a verified token subject partition history by caller; that does not authorise business-tenant access to tools, retrieval or telemetry.

For every shared layer, decide whether it is shared behind an enforced boundary or dedicated, including key and credential ownership, retention, deletion and usage limits. Dedicated resources can simplify a boundary but add provisioning, patching and clean-up.

For every shared layer, record two boundaries:

  • Enforcement: the permission or trusted filter that separates tenants. Namespaces, UI filters and session labels alone do not.
  • Failure and ownership: outages, noisy tenants, revocation and data cleanup. Security isolation does not guarantee capacity isolation.

Landing zone: why this layer comes first 5 min

With owners and boundaries decided, the next question is what everything stands on. Decide the network, the infrastructure layers and where telemetry lives before any shared service is built: endpoints, stores and readers, correlation, retention, redaction and sampling, and who pays.

An agent platform stands on three things:

  1. AWS accounts: where the platform's resources live.
  2. Network: how those resources connect.
  3. Infrastructure code: how the foundation is provisioned.

These form the landing zone. Build it first: changing accounts or networking later means moving the resources that depend on them.

The landing zone rests on four decisions. The accounts and the operating model are already decided above; this part makes the network and infrastructure decisions and adds two for telemetry:

  1. Accounts: how many do you need, where do resources run, and who may administer them?
  2. Network: public access, private access with NAT, or private endpoints only?
  3. Infrastructure: who creates it, and how?
  4. Operating model: who builds, releases, supports and operates the shared services and agents?

Agree who runs what before finalising the layout. A federated operating model does not determine account count. Account layouts can change without changing responsibilities.

This workshop. We choose C to prevent internet access from the VPC. One private VPC spans the three Availability Zones supported by AgentCore Runtime and has two subnet types:

  • App subnets: the LiteLLM proxy and its internal load balancer, the relay Lambda, the interface endpoints and, from Module 4, the network interfaces of the agent harnesses. A harness is AgentCore's configuration-driven agent, the form our agents take in Module 4; workshop apply 1 already creates the security group agent-platform-harness for them.
  • Data subnets: the database, and nothing else.

Both groups are isolated subnets. Their route tables know the VPC itself and the S3 gateway endpoint, nothing more, so neither has a path to the internet. The data subnets are a separate group only so the database sits in its own address range, apart from the application components; its security group accepts PostgreSQL from the LiteLLM tasks alone and allows no outbound connection at all. The agent harnesses run in VPC mode. There is no internet gateway, NAT gateway or public IP anywhere in the VPC.

AWS services are reached through two kinds of endpoint:

  • Nine interface endpoints, which the VPC console and the workshop apply 1 output name by service: bedrock-runtime (the proxy's model calls), bedrock-agentcore (the AgentCore data plane: Runtime, Memory and Identity), bedrock-agentcore.gateway, secretsmanager, logs and monitoring (CloudWatch logs and metrics), xray, and ecr.api with ecr.dkr for image pulls. There is no endpoint for the AgentCore control plane: nothing inside the VPC creates or configures AgentCore resources; the control plane does that from outside.
  • One gateway endpoint: S3.

Without internet access, tasks must pull the LiteLLM image from private ECR. workshop apply 1 copies it into your account first, adding a few minutes to deployment.

The quoted hourly estimates cover two components:

  • Endpoints: about 0.18 USD per hour (nine endpoints in two zones).
  • Proxy: about 0.10 USD per hour.

The database is single-AZ for the workshop.

Outside the VPC. The control plane's web UI, API and worker remain outside, along with Cognito and Agent Registry.

Those two services have no PrivateLink endpoints. A control plane in an isolated VPC could not manage sign-in or read the catalogue. Its AWS management calls use IAM authentication and TLS.

Module 2 adds one more thing outside this VPC: the corporate identity provider, Keycloak, which stands in for the Okta or Entra ID a company already runs. workshop apply 2 gives it a small public VPC of its own (10.1.0.0/16: two public subnets, an internet gateway, no NAT, no endpoints), because a company's identity provider must be reachable over the public internet: AgentCore Identity and API Gateway fetch its discovery document and call its token endpoint there, exactly as they would for a SaaS provider. Keycloak itself sits behind an internal load balancer, with an API Gateway HTTP API as its HTTPS door. The two VPCs are never connected, and the landing zone you build here stays as described.

The internal load balancer cannot be called directly from outside the VPC. Three callers therefore use the relay Lambda:

  • The control plane: the platform API and worker Lambdas.
  • The workshop command and the doctor on your laptop (the doctor runs at the end of workshop apply 1).
  • Other code on your laptop: the agent code exported in Module 4. workshop export --run starts a small local proxy that forwards its calls through the relay.

The relay forwards HTTP requests without adding credentials. IAM controls relay invocation; the proxy also requires its master key. The model route in Module 2 revisits this flow and explains why the proxy's admin console is unavailable in a browser.

Production path. Add three controls to this private network:

  1. Multi-AZ database: run the database across more than one Availability Zone.
  2. Endpoint policies: restrict each interface endpoint's access and scope the S3 endpoint to the platform's buckets.
  3. AWS WAF: protect the internet-facing web UI and API.

The organisation administrator creates an organisation domain from the management account; centralisation rules need the management account or a delegated administrator. Trace centralisation needs Transaction Search in each source account. Centralisation copies new telemetry once a rule is active; it does not backfill, while first-time enablement can backfill up to seven days of eligible local data (not data encrypted with a customer-managed key).

Access: members read the whole space by default; grants combine, including group grants, and have no explicit denies. Data scopes filter log and trace rows at read time, not fields within a visible row, and do not isolate metrics, dataset export, AI summaries or prompt playgrounds. A tenant attribute or dashboard filter cannot establish customer isolation; for strict separation use account or space boundaries, or a separately authorised customer view. Both a member's grant and the space's underlying access role must permit an operation.

Per request, require service name, environment, trace and span context, version identifiers, result and duration; propagate trace context across calls and link asynchronous work explicitly. Publish session.id on each turn's root span; gen_ai.conversation.id alone does not group sessions. The trace endpoint requires SigV4. These are correlation fields, never authorisation claims. Keep control-plane audit events separate from execution traces.

Content: redact at capture when content must never leave the process; collector filters and log masking are extra layers, not substitutes. A customer-managed key needs attaching-principal, service, forwarding-role and reader permissions. Record retention for source logs, datasets, centralised copies, evaluation artefacts and exports.

Detection: choose trace sampling and online-evaluation sampling separately; sampled spans make request and token counts incomplete. An alert needs its own access profile, a no-data rule and a notification rule; without one it sends nothing. A short-lived heartbeat distinguishes an idle workshop from a broken pipeline.

Review the complete target architecture: follow the two request paths

Every decision so far constrains one platform. The target architecture at the end of this page is that platform as the workshop plans to build it over Modules 2 to 5; it is the planned target, not something already deployed. Before reviewing it as a whole, follow the two kinds of request it must carry, because each one crosses the boundaries you placed above.

Platform actions: a persona signs in through Cognito, calls the authenticated platform API, and receives only actions allowed by their role. The API records state and dispatches work. The worker coordinates deployment, evaluation, invocation and promotion.

Agent invocation: the Playground or workshop ask reaches the HR runtime through the control plane. The runtime calls the private model gateway with its scoped model key and calls tools through its configured AgentCore Gateway. Tool targets and the HR Knowledge Base supply the result. Traces and metrics connect the request to its runtime, tool calls and outcome.

The employee-aware variant uses a different identity path: a corporate employee token enters the on-behalf-of runtime and gateway, and an outbound token exchange supplies the HR API's required audience. Keep that employee identity separate from the platform persona and the runtime's AWS execution role.
