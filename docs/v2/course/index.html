Why an agentic AI platform

Without a platform, independent teams each repeat the same shared capabilities and controls: sign-in, tool access, model keys, guardrails, budgets, release checks and monitoring, each built a little differently.

An agentic AI platform builds those capabilities once and offers them to every project, so a team writes the part that is its own, the use case, and inherits the rest with the organisation's rules already applied.

How an organisation uses it

A platform team runs the shared capabilities. Project teams in each business domain build agents on them. A domain approver accepts an agent's business behaviour before it reaches Prod. You play all of these roles during the day (module 2 introduces the personas).

Two example workflows exercise the platform; neither is the point of the day:

  • HR assistant (People Operations): the agent you take through the whole path, from blueprint to Dev, evaluation, approval and Prod, running under its own service identity. A separate on-behalf-of variant in Dev, never released, demonstrates carrying an employee's identity to the HR tools.
  • Invoice helper (Finance Operations): one tool and no agent. It exists to prove isolation: module 3 shows that HR's agent role cannot call the Finance tool directly, and module 4 shows that Finance's role is refused at HR's gateway. It is never released.

Built progressively

The modules follow the order an architect decides in: the landing zone first, because everything stands on it, then identity, governance, tool access, model access, delivery and operations. Each layer uses the ones below it.

Reading a decision

Every module asks a few design questions. Two labels keep the reference answer and the lab apart:

  • Recommended marks the reference option for a production platform, where one is defensible, and it comes first as A.
  • This workshop marks what the lab builds. It can differ from the recommendation, because an event account is one account with no corporate identity provider.

A tag under each question says what kind it is: choose one options exclude each other; patterns combine are used together, each in its own situation (approvals in module 6 and evaluation approaches in module 7 are examples); depends on context has no universal winner.

How you'd build

① Architecture

② Request flow

Step-by-step explanation
  1. User invokes the AgentCore Harness endpoint with a session id. Agent runs the session in its own microVM.
  2. The harness fetches its virtual key from the AgentCore Identity token vault and calls LiteLLM. LiteLLM enforces model allow-list, rate limits and budgets for the project (via virtual key), applies the Bedrock guardrail attached to the model alias, calls Amazon Bedrock, and records usage and cost.
  3. If the model asks for a tool, the harness calls the project AgentCore Gateway. The Policy engine evaluates the Cedar policies for the harness's execution role, the tool and its arguments, then the gateway invokes the Lambda tool or the knowledge-base connector.
  4. Memory events are written for the session. A long-term strategies extract summaries and preferences asynchronously.
  5. The answer streams back with usage metadata. Spans and metrics land in CloudWatch. The spend row lands in LiteLLM; Online evaluation scores the session with a few minutes delay asynchronously.
All model requests goes through the Model Gateway (LiteLLM). All tool access goes through the AgentCore Gateway.
These two choke points enforces who may use what, how much, and under which rules.

③ Release flow

Step-by-step explanation
  1. workshop apply 6 (or the Releases screen) stores blueprint version n; the worker creates the immutable Harness version and deploys it to the Dev harness.
  2. The evaluation run invokes the Dev endpoint for every scenario, waits for telemetry, and scores each scenario with built-in evaluators. The worker runs it for a release created on the Releases screen (or with Run evaluation); workshop apply 6 runs it itself and posts self-reported scores.
  3. The platform compares scores with the thresholds in the blueprint and marks the release BLOCKED or PENDING_APPROVAL.
  4. The Domain approver reviews the evidence in the UI and approves.
  5. The worker runs promotion from the UI or API: it renders the same blueprint for Prod (Prod gateway, memory and key, creating the Prod key when missing), updates the Prod harness to a new immutable version, and ensures online evaluation is monitoring it.

How the day builds the platform

The control plane is already deployed for you.
Each module adds one layer of your own platform foundation. At the end you own a complete, governed platform with one agent in production.

The build path you follow

Each layer could be built in several ways; the course discusses them and then builds one path, the same for everyone:

  1. workshop apply 1: one account with Dev and Prod by name, a private VPC with endpoints only, and the LiteLLM model gateway.
  2. workshop apply 2: Cognito groups for the three personas, and Keycloak as the employees' login for the on-behalf-of chain.
  3. workshop apply 3: the People Operations and Finance Operations domains, one project each, with roles and a model budget stamped from templates.
  4. workshop apply 4: one gateway per project and environment, a shared Cedar policy engine, the catalogue, and the on-behalf-of gateway.
  5. workshop apply 5: a capped model key in the token vault, and the catalogue approvals.
  6. workshop apply 6: the HR assistant's blueprint through one platform-owned CodePipeline: deploy to Dev, evaluate, approve, promote.
  7. workshop apply 7: Prod traffic, online scores, policy decisions and spend in one view.

Already pre-provisioned? If your facilitator deployed the landing zone before the day, module 1 runs workshop apply 1 --no-deploy to inspect it instead; every other step is the same.
