Two layers, one order Explain · 5 min

By the end of the day your account holds two kinds of things. The first kind is the stacks, which CloudFormation created. The second kind is what the modules created at run time through the platform: agents, gateways, policies, memories, keys and projects. CloudFormation deletes only the first kind, because no stack knows about an object that an API call created later. So the order matters: we remove the run-time objects first, while the platform API is still there to do it, and take the stacks down after that.

Glossary
Stack
one CloudFormation unit of resources, created and deleted together. Think: a prefab module of the building.
cdk destroy
the CDK command that deletes stacks, in reverse dependency order.
Run-time object
something an API call created after the stacks existed; no stack knows about it. Think: furniture, not walls.
Shared object
the policy engine and the catalogue registry: one per account, used by every project. Deleted at the end of their own step, and only when nothing else uses them.
Asynchronous deletion
AgentCore answers "deleting" and finishes minutes later; harnesses and memories take 2 to 8 minutes.
Sweep
the script that removes what CloudFormation leaves behind: secrets in their recovery window, log groups recreated by late log delivery, orphan buckets.

The last step, step 9, lists whatever still carries your names, and that list must be empty. You can run the clean-up more than once without harm, because every step looks before it deletes and tolerates "already gone". So if a run stops halfway, you simply start it again.

This workshop. We remove everything, stacks included. In an event account the clean-up is optional, because Workshop Studio deletes the whole account after the event. We still ask you to run it once, because the order in which things come down teaches you what a stack knows about, and what it does not.

Production path. Deletion is written as code. The control plane gets an "offboard project" job that runs the same steps you run today, and the stacks get a stage of their own in the pipeline.

Hands-on 25 min · 10 attended

Reverse the day
  1. commandworkshop cleanup --dry-run: the inventory by name. What you built, what is shared, what belongs to others. Nothing is deleted.
  2. commandworkshop cleanup, then type yes. Nine steps in reverse order; most of the ten minutes is AgentCore deleting harnesses and memories in the background. If it stops, run it again.
  3. screenPlatform UI: Domains and projects is empty; Governance shows no gateways. AgentCore console: no harness, gateway or memory with your names.
  4. commandworkshop cleanup --stacks, answer yes to each prompt: cdk destroy of the eight stacks, the corporate IdP included, about 13 minutes, then the sweep. Your own account; in an event account this step is optional.
  5. commandworkshop status: eight times not deployed. CloudFormation console: of the workshop's stacks only CDKToolkit is left.
  6. recordAdd two lines to the module 7 backlog in design-record.yaml: who deletes what in your organisation, and how deletion is tested.

Once the stacks are gone, the cost stops with them. If the deletion seems to pause on the ModelGateway or the Network stack, nothing is wrong: it is waiting for the relay Lambda's network interfaces to be released, which can take up to about 20 minutes. A few things stay in the account on purpose: the Transaction Search setting, the two AgentCore Runtime service-linked roles (one for the runtime's identity, one for its network interfaces in your VPC), the CDK bootstrap stack, Bedrock model access and the metric history. Of these, only the bootstrap bucket costs anything, and that is cents per month.

Remember. Whatever you build up, you tear down in reverse order. If deleting turns out to be hard, you built without thinking about how you would leave.
