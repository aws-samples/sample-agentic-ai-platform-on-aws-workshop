What the platform gives teams

Build a platform that gives teams supported ways to find approved capabilities, obtain access, call tools and models, and release agents. HR and Finance are the two workloads that test whether those shared boundaries work.

The course groups capabilities by when their decisions matter:

WhereCapability
Module 1Requirements and acceptance cases; platform personas and the operating model; account placement, business tenancy and administrative ownership; landing zone and telemetry placement; a reviewed request flow
Module 2: foundation and identityPrivate network, endpoints and shared services; persona sign-in and an administrative denial; credential stores; the corporate login for employees and its credential providers
Module 2: model accessOne governed model route: safety, spend control, processing location and the shared model gateway's health
Module 2: registry and gateway accessRegistry setup and identity; whether a shared tool gateway is needed, with its identity and policy; how a coding assistant discovers and invokes approved tools
Module 2: control planeThe control plane: UI, API, state and worker; domains, projects, roles and budgets; what it creates and what it only registers
Module 3HR and Finance: workload identity and delegation, workload gateways, tools, knowledge and blueprints
Module 4Discovery and access requests, scoped model keys and caps, isolation review, evaluation, independent approval and promotion
Module 5Traffic and traces, unit cost, audit and incidents, online quality and the production backlog

A coding assistant appears as a consumer of the registry and gateways during Module 2's client-access exercise; there is no separately hosted coding workload. HR carries the full runnable lifecycle (blueprint, Dev, evaluation, approval, Prod, operations). Finance proves tool isolation with an invoice fixture and gets a blueprint design; deploying a Finance agent is an extension with named prerequisites.

Who you are during the day

You make the design decisions as a platform architect, then act as three signed-in platform personas. Module 1 introduces them and Module 2 creates them.

PersonaOwnsBoundary
Platform adminShared services and templates, domains and projects, model and tool envelopes, catalogue approval, budgets and caps, policy modeAdministering the platform does not authorise accepting a workload's release
Agent developerThe workload: blueprint and prompt, Dev deployment, evaluation, release submissionCannot administer the platform or approve its own release
Domain approverBusiness behaviour: approves or rejects a specific release and promotes itApproval names the exact candidate, domain and environment

The employee (Alex Rivera, E1001 in the sample data) is not a persona you wear. Employees reach an agent through a business channel and sign in at the corporate identity provider; their identity and data entitlement differ from platform personas and from the service roles agents run under.

Practise the handoff early: if an HR tool fails after a shared policy change, name who owns the tool, who owns the gateway policy, which running version was affected and what evidence each needs. A domain name alone does not settle these responsibilities.

Try the ownership boundary

For each change, decide what the platform team supplies and what stays with the workload owner, then compare with the worked answer:

ChangePlatformWorkload
A team needs another approved modelReview the model route, guardrail and access policy; add it to the project's allowed modelsCheck that the model meets the task and performance needs
A team wants to reuse a customer-record toolProvide target onboarding, credential handling and an authorisation contractObtain the data owner's approval; bind the permitted tool version and scope
A request fails during a tool callMake correlated telemetry available to permitted operatorsEmit workload and version context; investigate the business request with the tool owner

Save one row adapted to your own outcome sentence. Sharing a service reduces duplicated implementation but creates a dependency on its availability and change process; a requirement for independent administration or a different data boundary may justify a dedicated resource.

A guide, if you use one. No assistant is packaged with the workshop. The guide prompts on some pages work with any assistant you are allowed to use: it should read what you already decided, ask only for information that could change the recommendation and keep its rationale in your record. "Use the supplied implementation because it meets this requirement" is a valid answer. A recommendation is not evidence: deployment and verification need their own records.

Two records

design-record.yaml in the implementation package holds the inputs the workshop command reads and your own calls for each decision. The journey record holds your chapter progression, requests, resource references and observed evidence. Neither replaces the other.

Reconcile the assignment with what you can see

Outcome: an environment note that separates supplied resources, participant work and unresolved access checks.

You need the event invitation and participant access instructions. Open the event page, then the assigned AWS console and the editor workspace. Keep the event page open in a browser tab: it holds your console access and your AWS credentials.

  4. Mark each resource as event-managed or participant-managed. Confirm the clean-up owner and support route before changing anything.

Self-paced setup

Plan an isolated environment in an account you control. You own its charges, access and clean-up.

Get startedself-paced path

Build the environment plan

Outcome: an environment plan with a clear decision about whether resource creation can proceed.

You need an AWS account, permission to deploy CloudFormation stacks and create IAM roles in it, and the implementation package (the workshop command, its SDK, scenario and infrastructure code). Use a sandbox whose existing resources you can identify and preserve. The lab stays in one account even if your Module 1 design spans several.

  1. Record the account and Region. The implementation defaults to us-east-1 and its model aliases map to us. cross-Region inference profiles; another Region needs its own qualification of model and service availability.
  2. Note that the implementation uses fixed resource names (for example AgentPlatform-* stacks and agent-platform-* roles): one copy per account and Region. Identify existing stacks and account-level settings, such as CloudWatch Transaction Search and the CDK bootstrap stack, that the lab must preserve.
  3. Record a spending limit, a clean-up time and who will inspect remaining resources. Estimate costs with the AWS Pricing Calculator. Include idle infrastructure: while deployed, the landing zone costs about 0.28 USD per hour (proxy and database about 0.10, nine interface endpoints about 0.18) and the corporate identity provider about 0.08 more. Model usage stops when requests stop; endpoints, the proxy and log retention keep billing.
  4. Deploy the four pre-day stacks yourself, since no facilitator does it for you: from the package root run uv run workshop deploy pre-day and wait for AgentPlatform-Web, -Auth, -Platform and -Scenario to reach CREATE_COMPLETE. This needs the CDK bootstrap stack in the account and Region.

Keep the central Okta credential separate

The event editor can load an Okta administration credential from the event's central account with source /usr/local/bin/load-central-okta-env. It exports WKS_OKTA_ORG_URL, WKS_OKTA_TOKEN and WKS_OKTA_EVENT for the wks-okta provisioning tool, which creates or removes Okta objects for the event. It is an event-administration credential with organisation-wide Okta permissions.

It is not part of the platform's identity design:

  • Platform personas sign in at the platform's Cognito user pool, configured in Module 2.
  • Employees sign in at the corporate identity provider the labs deploy, Keycloak, configured in Module 2. Their identity reaches tools by token exchange in Module 3.
  • Agents and gateways use IAM execution roles and AgentCore Identity credential providers, configured alongside the shared services in Module 2 and applied to workloads in Module 3.

Never place the Okta token in agent prompts, client configuration, the design record or evidence. If your organisation's employees use Okta, Module 2's identity design explains what replaces Keycloak; that replacement is a design change, not something the provisioning token configures.

The journey record

Download the journey-record template and save it in your workspace. Fill in context, environment reference, desired outcome and next action. Use an anonymised customer scenario or the fictional Northstar example in Module 1.

Fill later sections as you reach them. Keep shared capabilities and workload resources in separate sections: a configured gateway and a working business tool are different checkpoints. For each decision, record the reason, the accepted trade-off and a trigger to reconsider it, for example: "Use one shared tool interface to avoid maintaining two connectors. Accept dependence on the platform team's change process. Revisit if the teams need incompatible data-access policies."
