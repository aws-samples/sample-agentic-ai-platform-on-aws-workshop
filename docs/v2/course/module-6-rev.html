From platform to workload Explain · 10 min

The shared platform is ready. Now switch from Platform admin to Agent developer and build a workload in five steps:

  1. Build: write a blueprint.
  2. Deploy: render it for Dev.
  3. Evaluate: compare scores with thresholds.
  4. Release: obtain Domain approver approval.
  5. Promote: render the approved blueprint for Prod.
Run 1 · start now · about 12 to 15 minutes

Check that module 5's Dev cap is restored. In design-record.yaml, set prompt_version: v1 under module_6.inputs, then run workshop apply 6. It waits about two and a half minutes for the two memories to become active, four to five minutes for the first Dev deployment (the first harness in the VPC waits for its network interfaces; later versions and the on-behalf-of twin reuse them and take under a minute), and five to six minutes for the evaluation. The planted prompt bug should produce a BLOCKED release. Continue reading while it runs.

Why start with a blueprint?

A blueprint offers four benefits:

BenefitBlueprintCode from scratch
Governed constructionApproved references; platform resolves roles, keys, memory and guardrailsWire the same controls into code
Consistent buildsOne file for Dev and Prod; render takes secondsOwn builds and prevent environment drift
Reviewable changesSmall YAML and prompt diffs; evaluation catches regressionsReview use-case changes among framework code
Portable releaseBlueprint stays the release unit across implementationsKeep framework details out of the release contract

Tradeoff: this Harness configures one Strands Agents loop. Custom multi-agent graphs, branching workflows or existing frameworks need the code path.

The contract has two rules:

The agent that acts on your behalf

The Dev and Prod harnesses are called with SigV4 (Playground, evaluation, workshop traffic) and reach their tools as the project's agent role: the service identity of decision 2.2. A SigV4 call carries no employee, and AgentCore propagates no per-user identity downstream from it, so there is nothing to exchange. The on-behalf-of chain (2.5, 4.5) therefore gets a harness of its own. workshop apply 6 renders the latest blueprint for Dev once more and patches three things:

  • Inbound: a JWT authorizer that trusts the realm anycompany and accepts the audience hr-agent.
  • Tool gateway: the on-behalf-of gateway of module 4, called with OAuth TOKEN_EXCHANGE through the provider kc-hr-agent for the audience hr-obo-gateway.
  • Memory: off. One question needs none, and a memory would need an actor id per employee.

The result is hr_assistant_dev_obo, the twin of hr_assistant_dev: the same model alias, prompt, limits and agent role, plus one inline policy on that role, obo-token-exchange. The policy does two things: it lets the role ask AgentCore Identity for the exchange through kc-hr-agent, and it lets the twin fetch its model key from the token vault under its own workload identity, harness_hr_assistant_dev_obo-*, which the role template does not cover because it names only the Dev harness's identity, harness_hr_assistant_dev-*. The twin is called over HTTPS with Authorization: Bearer and the employee's token T0, not with a signed request. Before every tool call the harness hands T0 to AgentCore Identity, which exchanges it at Keycloak for T1; the gateway exchanges again, and the HR API receives T2. The harness code never sees a secret or an exchange. The Dev and Prod harnesses are untouched, and the twin is neither released nor promoted: it proves the identity chain from the employee's login to the tool's log line.

This workshop. Use a YAML blueprint with the Harness. When configuration is insufficient, export to Strands Agents or LangGraph; both are available. Code keeps the alias, tools, role and prompt, and adds its own memory, limits, tracing, deployment and gate.

Memory has two boundaries:

  • Environment: one memory per project and environment; Dev and Prod do not share it.
  • User: the caller supplies the user ID. The agent does not guess it. Events expire after 30 days. The on-behalf-of twin takes the person from its token and runs without memory.

Network: VPC mode connects Runtime through interfaces in the private app subnets and Harness security group. Render fixes this configuration. Initial interface creation adds deployment time; model and shared-service calls need no internet path.

Production path. Use containers for custom orchestration, keeping the blueprint as the release unit. MCP servers on Runtime follow the same gate and promotion.

6.2How does a release pass?

OptionProsConsChoose when
A dataset run with built-in evaluators and thresholds, then a humanrepeatable; a regression is caught before Proddataset evaluation is public preview; a dataset to maintainalways
Human review onlycheap to startno repeatabilitythe first weeks
Online evaluation onlyreal trafficproblems reach users firstlow-risk agents

This workshop. The release gate has four parts:

  1. Dataset: ten scripted conversations against Dev.
  2. Evaluators: Correctness, GoalSuccessRate, TrajectoryInOrderMatch and Harmfulness.
  3. Thresholds: all four must pass; otherwise BLOCKED. Three are floors on the mean score. Harmfulness is the one ceiling: the judge scores a harmless answer 1, and the gate compares the harm rate (1 minus the mean) with 0.0. That is why the figure's 0.0 for Harmfulness is a harm rate, not a mean, and why the Releases screen shows a mean score of 1.0 beside a compared value of 0.0; a single harmful answer blocks the release.
  4. Human: a passing release waits for Domain approver approval.

The v1 prompt skips the knowledge base; v2 fixes the instruction. Compare each run's scores. Two paths run the gate today, and both use the thresholds of the team's blueprint. workshop apply 6 runs the dataset from your machine and posts the scores, which the platform records as self-reported. A release created on the Releases screen, or run again there with Run evaluation, is run by the platform's worker instead: it deploys the version to Dev when the Dev harness does not run it yet, runs the same dataset and applies the thresholds, and the release page shows each step as it happens.

Production path. Platform-run evidence only (no self-reported scores), platform-owned minimum thresholds and approvals bound to the evaluated run.

This workshop. Promotion performs three actions:

  1. Resolve: the approved blueprint against Prod's gateway and memory, and ensure the Prod key. No Prod key exists yet: module 5 created the Dev key only, so the first promotion creates hr-assistant-prod-claude-sonnet-5 with the blueprint's cap (1 USD per 7 days) and stores it in the token vault; the project's Keys tab then shows two keys, each with its own spend.
  2. Deploy: create the Prod Harness and pin live to its version.
  3. Observe: register the online evaluation that module 7 reads. hr_assistant_prod_online_eval watches the live endpoint's spans and scores every Prod conversation (100 % sampling) with three judges, Helpfulness, Harmfulness and ToolSelectionAccuracy; scores arrive 8–11 minutes after a conversation goes quiet. This is a different set from the gate's four (only Harmfulness is in both): the gate compares each answer and tool sequence with the dataset's expected ones, and live traffic has no expected answers, so these judges score each conversation on its own.

A platform worker runs promotion from the UI or API. A Git pipeline is discussed as a take-home path; it is not built today.

Production path. Drive promotion through a Git pipeline calling the platform API, with a second Prod approver.

From blueprint to Prod

Check the two runs started earlier:

  1. v1: memory (about 2.5 minutes), blueprint, first Dev deployment (4 to 5 minutes: the first harness in the VPC), a warm-up question (about 35 seconds), the on-behalf-of twin of the Dev harness (about half a minute) and evaluation (5 to 6 minutes): 12 to 15 minutes in all.
  2. v2: corrected prompt, new Dev deployment, on-behalf-of twin, release and evaluation; about 6–7 minutes.

Read the output as it comes. The memory step creates the Dev and Prod memories and, on the first run only, writes two sample conversation events for employee E1001 (Alex) into the Dev memory: a stated preference for two-week leave blocks in August. AgentCore Memory extracts long-term preference records from them a few minutes later; workshop apply 7 reads them back. The blueprint step prints the Company policy questions section of the prompt it stores: the one section that differs between v1 and v2, and exactly where v1 goes wrong. After deploy to Dev the command asks the new version one policy question (the remote-work question from the evaluation dataset), labelled warm-up: this first call carries the cold start of a new harness version, 35 to 40 seconds, and shows the prompt's behaviour before the evaluation runs. With v1 the answer comes from general knowledge, the tools list on that line is empty and no document is cited; with v2 the same line shows hrkb___Retrieve and the answer should cite the AnyCompany Remote Work Policy.

Three tokens, one person. The harness never saw a secret and never performed an exchange itself; it named a provider, and AgentCore Identity did the rest at Keycloak, once for the harness and once for the gateway. If step 1 fails with a sign-in error, the Keycloak task has restarted since workshop apply 2 and the employee is gone with it; run workshop apply 2 again. The command also prints where to look afterwards: the HR API's log group and the Keycloak admin console.

Remember. The team writes the use case; the platform resolves its permitted resources. Evaluate before promotion. Keep Prod on an approved version; rollback repoints its endpoint. When the person matters, identity travels in a token exchanged at every door, not in an argument.

The platform after module 6

One blueprint now runs in two environments: Dev DEFAULT follows its latest version; Prod live pins the approved version. Each has its own memory. Model calls use the private load balancer; Gateway, Identity and Memory use PrivateLink. A third harness, hr_assistant_dev_obo, stands beside Dev: the same render with a JWT authorizer at its door, its tool calls carrying the employee's exchanged token to the on-behalf-of gateway.

Glossary

Workload
An agent and its blueprint, memories, harnesses and releases.
AgentOps
Build, test, approve, promote, observe and improve agents.
Blueprint
YAML specification of model, prompt, tools, knowledge, memory, limits, budget and evaluation thresholds.
Harness
AgentCore's configuration-driven agent, using a Strands Agents loop.
Runtime
Managed compute for a Harness or custom agent code.
Render
Resolve blueprint references to an environment's gateway, memory, key and role.
Version, endpoint
Immutable numbered configuration; a named pointer to a version. Dev uses DEFAULT; Prod uses live.
Evaluator
A judge that scores an aspect of agent behaviour.
Release gate
Dataset evaluation against thresholds, followed by human approval.
Export, pipeline
Generate Strands Agents or LangGraph code; use CI/CD to test, deploy and release it.
On-behalf-of twin
hr_assistant_dev_obo: the Dev harness rendered once more with a JWT authorizer, so it can act for the employee who called it.
