From platform to workload Explain · 10 min

The shared platform is ready. This module decides what a project may do on it, then takes one project, the HR assistant, from a blueprint to Prod. Switch from Platform admin to Agent developer and build a workload in five steps; one AWS CodePipeline execution carries out the last four:

  1. Build: write a blueprint.
  2. Deploy: render it for Dev.
  3. Evaluate: compare scores with thresholds.
  4. Release: obtain Domain approver approval.
  5. Promote: render the approved blueprint for Prod.

One blueprint, one pipeline

Why start with a blueprint?

A blueprint offers four benefits:

BenefitBlueprintCode from scratch
Governed constructionApproved references; platform resolves roles, keys, memory and guardrailsWire the same controls into code
Consistent buildsOne file for Dev and Prod; render takes secondsOwn builds and prevent environment drift
Reviewable changesSmall YAML and prompt diffs; evaluation catches regressionsReview use-case changes among framework code
Portable releaseBlueprint stays the release unit across implementationsKeep framework details out of the release contract

Tradeoff: this Harness configures one Strands Agents loop. Custom multi-agent graphs, branching workflows or existing frameworks need the code path.

The contract has two rules:

  • Team chooses: use-case references within the project's allow-list.
  • Platform resolves: role, key, memory, gateway and network. The blueprint cannot replace these.

The agent that acts on your behalf

The Dev and Prod harnesses are called with SigV4 (Playground, evaluation, workshop traffic) and reach their tools as the project's agent role. A SigV4 call carries no employee, and AgentCore propagates no per-user identity downstream from it, so there is nothing to exchange. The on-behalf-of chain (Module 4) therefore gets a harness of its own. workshop apply 6 renders the latest blueprint for Dev once more and patches three things:

  • Inbound: a JWT authorizer that trusts the realm anycompany and accepts the audience hr-agent.
  • Tool gateway: the on-behalf-of gateway of module 4, called with OAuth TOKEN_EXCHANGE through the provider kc-hr-agent for the audience hr-obo-gateway.
  • Memory: off. One question needs none, and a memory would need an actor id per employee.

6.2How does a release pass: gates and approvals?

Gates and approvals that stack: each catches a different kind of fault, and a release passes them in order.

This workshop. The release gate has four parts:

  1. Dataset: ten scripted conversations against Dev.
  2. Evaluators: Correctness, GoalSuccessRate, TrajectoryInOrderMatch and Harmfulness.
  3. Thresholds: all four must pass; otherwise BLOCKED. Three are floors on the mean score. Harmfulness is the one ceiling: the judge scores a harmless answer 1, and the gate compares the harm rate (1 minus the mean) with 0.0. That is why the figure's 0.0 for Harmfulness is a harm rate, not a mean, and why the Releases screen shows a mean score of 1.0 beside a compared value of 0.0; a single harmful answer blocks the release.
  4. Human: a passing release waits for Domain approver approval.

The v1 prompt skips the knowledge base; v2 fixes the instruction. workshop apply 6 and the Releases screen start the same AWS CodePipeline execution, one per release, in four stages:

  1. Source: a versioned snapshot of the release.
  2. Validate: DeployDev, then Evaluate with the blueprint's thresholds. The stage stays locked across both, so another release cannot replace Dev mid-evaluation. A failed threshold ends the execution: the release is BLOCKED, and a fix is a new release.
  3. Approve: a manual gate the Domain approver releases.
  4. Promote: a second manual gate in the same execution, then PromoteProd.

The command only follows progress: it does not evaluate locally, and the API refuses self-reported scores.

Production path. Platform-run evidence only (no self-reported scores), platform-owned minimum thresholds and approvals bound to the evaluated run.

This workshop. There are two approval routes:

  • Catalogue record: Platform admin approves (module 5's hands-on).
  • Release: Domain approver approves and promotes; the Platform admin and the Agent developer get 403.

The API checks the caller's group, not whether the approver also submitted the release: separation of duties comes from keeping the developer and approver groups apart, as the three personas do.

Production path. Bind approvers to domains, require two for Prod, bind approval to its evaluation evidence and refuse self-approval by identity.

This workshop. Promotion performs three actions:

  1. Resolve: the approved blueprint against Prod's gateway and memory, and ensure the Prod key. No Prod key exists yet: module 5 created the Dev key only, so the first promotion creates hr-assistant-prod-claude-sonnet-5 with the blueprint's cap (1 USD per 7 days) and stores it in the token vault; the project's Keys tab then shows two keys, each with its own spend.
  2. Deploy: create or update the Prod Harness; its DEFAULT endpoint follows the new version.
  3. Observe: register the online evaluation that module 7 reads. hr_assistant_prod_online_eval watches the Prod harness's spans and scores every Prod conversation (100 % sampling) with three judges, Helpfulness, Harmfulness and ToolSelectionAccuracy; scores arrive 8–11 minutes after a conversation goes quiet. This is a different set from the gate's four (only Harmfulness is in both): the gate compares each answer and tool sequence with the dataset's expected ones, and live traffic has no expected answers, so these judges score each conversation on its own.

CodePipeline owns the release sequence. Approve and Promote remain separate actions on the Releases screen, each releasing a native manual gate through the authenticated platform API. The Promote action deploys Prod and registers online evaluation. Executions queue at each stage: an approval holds later releases at that gate, while earlier stages can continue.

Production path. This workshop starts a pipeline from an immutable blueprint snapshot. A Git-triggered build for exported Strands or LangGraph code is a separate extension; it is not part of this release pipeline.

Hands-on 20 min

From blueprint to Prod

Check the two runs started earlier:

  1. v1: memory (about 2.5 minutes), blueprint, first Dev deployment (4 to 5 minutes: the first harness in the VPC), the on-behalf-of twin of the Dev harness (about half a minute) and evaluation (5 to 6 minutes): 12 to 15 minutes in all.
  2. v2: corrected prompt, new Dev deployment, on-behalf-of twin, release and evaluation; about 6–7 minutes.

The memory step prepares Dev and Prod memory; the blueprint step stores the selected prompt and thresholds. CodePipeline then deploys Dev and evaluates it. The CLI prints the execution identifier and waits for the verdict. Use the Releases screen and CodePipeline execution to inspect each stage. After evaluation, the command prepares the on-behalf-of twin for the later exercises. With v1, expect BLOCKED; with v2, expect PENDING_APPROVAL. Queued executions can take longer while another release awaits a decision.

Three tokens, one person. The harness never saw a secret and never performed an exchange itself; it named a provider, and AgentCore Identity did the rest at Keycloak, once for the harness and once for the gateway. If step 1 fails with a sign-in error, the Keycloak task has restarted since workshop apply 2 and the employee is gone with it; run workshop apply 2 again. The command also prints where to look afterwards: the HR API's log group and the Keycloak admin console.

Remember. The team writes the use case; the platform resolves its permitted resources. Evaluate before promotion. Keep Prod on an approved version; roll back by promoting the previous one again. When the person matters, identity travels in a token exchanged at every door, not in an argument.

The platform after module 6

One blueprint now runs in two environments, each reached through its harness's DEFAULT endpoint: Dev follows the latest deploy; Prod follows the latest promotion. Each has its own memory. Model calls use the private load balancer; Gateway, Identity and Memory use PrivateLink. A third harness, hr_assistant_dev_obo, stands beside Dev: the same render with a JWT authorizer at its door, its tool calls carrying the employee's exchanged token to the on-behalf-of gateway.

Glossary

Workload
An agent and its blueprint, memories, harnesses and releases.
Project blueprint
Course name for a project's path to Prod: the Project definition the admin onboards (module 3) and the AgentBlueprint the team writes; the platform renders, tests, approves and promotes it. The two artifact kinds keep their names.
Delivery
Build, test, approve, promote, observe and improve agents (often called AgentOps).
Blueprint
YAML specification of model, prompt, tools, knowledge, memory, limits, budget and evaluation thresholds.
Harness
AgentCore's configuration-driven agent, using a Strands Agents loop.
Runtime
Managed compute for a Harness or custom agent code.
Render
Resolve blueprint references to an environment's gateway, memory, key and role.
Version, endpoint
Immutable numbered configuration; a pointer to a version. Both environments use DEFAULT, which follows the latest version (named endpoints are denied in the event accounts).
Evaluator
A judge that scores an aspect of agent behaviour.
Release gate
Dataset evaluation against thresholds, followed by human approval.
Export, pipeline
Generate Strands Agents or LangGraph code; a project-owned pipeline would test and deploy it, then hand the release to the platform's gate (discussed, not built).
On-behalf-of twin
hr_assistant_dev_obo: the Dev harness rendered once more with a JWT authorizer, so it can act for the employee who called it.
