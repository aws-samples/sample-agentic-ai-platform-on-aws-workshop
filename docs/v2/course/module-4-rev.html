One door for every tool Explain · 10 min

AgentCore Gateway exposes tools through MCP, a common agent-to-tool interface. It provides three controls:

  1. Caller: who may reach the gateway.
  2. Operation: which tool and arguments are allowed.
  3. Evidence: what happened on each call.

Production path. Row-level security is the next step, and there are two places to put it. Either the tool reads the person from the token and ignores the argument, or a Cedar rule at the gateway forbids a call whose employee_id argument differs from the token's employee_id. Either way, attach the on-behalf-of gateway to the policy engine, start in LOG_ONLY as in decision 4.3, and keep the evidence line in the tool's log, because it is the record of who was really served.

This workshop. Topology A, built once per environment, creates three gateways:

  • HR Dev and HR Prod: separate environment access.
  • Finance Dev: the caller used to test isolation.

Each agent signs with IAM. All three gateways share one policy engine. Gateway ownership and target-account placement are separate decisions. A fourth gateway, hr-assistant-dev-gw-obo, stands beside HR Dev for callers with a token from the corporate IdP (explained above); it does not change the layout question.

Production path. Combine the topologies: a platform gateway for shared tools, domain gateways, and project gateways for private tools. Specialist agents can later become gateway targets themselves; carry identity and apply policy at every hop. All gateways still share the account's quotas.

Environment isolation is the second dimension, and it applies to every topology above:

The workshop builds two environments, Dev and Prod. There is no staging environment.

Quotas apply at two levels (limits at writing):

  • Gateway: 100 targets; 200 tool calls or lists per second.
  • Account: the same 200-per-second ceiling across gateways. Four gateways, the three above and the on-behalf-of twin, do not make it 800; a 250-per-second forecast needs a quota increase.

4.2How are tool policies rolled out?

OptionProsConsChoose when
RecommendedThis workshop

This workshop. Roll out the shared engine in three steps:

  1. Write: a permit per tool and a deny for leave requests over 10 days.
  2. Observe: LOG_ONLY records Allow/Deny metrics.
  3. Enforce: admin switches HR Dev to ENFORCE and repeats the denied call.

Policies are handwritten Cedar so you can inspect the stored rules. Natural-language generation is optional.

Check three kinds of evidence:

  • Bypass permissions: step 8 inspects the agent role's lack of direct Lambda access. It does not execute a bypass call.
  • Data scope: the KB filter is pinned; employee-ID checks remain a gap in Lambda tools.
  • Actual refusal: step 7 executes tools/call. READY or tools/list alone does not prove enforcement.

Mode today: workshop apply 4 sets the record's one gateway_mode, LOG_ONLY by default, on all three IAM gateways, HR Prod included, and a re-run sets them back to it. You flip HR Dev to ENFORCE; workshop apply 6 requires that, because its dataset expects the leave-days deny. HR Prod stays in LOG_ONLY unless you flip it on the Governance screen. The lab has Dev and Prod only, no staging.

Production path. Run Prod gateways in ENFORCE, and set the mode per environment rather than once for all. Give policy-owning domains their own engines. Review changes as code before attaching them to gateways.

Then the fourth door: gateway hr-assistant-dev-gw-obo (inbound CUSTOM_JWT, realm anycompany, audience hr-obo-gateway) and its target hrapi, the HR API as an OpenAPI target with OAUTH TOKEN_EXCHANGE towards hr-tools-api. Look for hr-assistant-dev-gw-obo READY CUSTOM_JWT (aud hr-obo-gateway) and target hrapi READY OpenAPI https://... (4 operations), OAUTH TOKEN_EXCHANGE -> aud hr-tools-api.
  3. commandworkshop call --as hr-dev get_leave_balance E1001 → leave balance.
  4. commandworkshop call --as finance-dev get_leave_balance E1001 → HTTP 403. IAM prevents Finance from reaching HR's gateway.
  5. commandworkshop call --as hr-dev submit_leave_request E1001 15 → the result line reads OK allowed: {"error": "Insufficient annual leave balance: E1001 requested 15 days but has 12 days available."}. Read it in two halves. allowed means the gateway let the call through to the tool: your max_leave_days forbid rule did match, but in LOG_ONLY the engine only records that deny and does not act on it. The error text is the tool's own refusal: E1001 has 12 days, so no request is created. Nothing at the gateway blocked the call; the deny appears only as a Deny count on the Overview chart (CloudWatch DenyDecisions), which can take up to four minutes. The OK prefix is on every workshop call result line, including the 403 and the -32002 in the other steps; it means the command ran, not that the call was allowed.
  6. screenAs Platform admin, open Governance. In the Policy engine and gateways table find the row with project hr-assistant and env dev (its Gateway id begins with hr-assistant-dev-gw; the on-behalf-of gateway is not listed there), flip the toggle in the Enforce column and confirm with Set ENFORCE. UpdateGateway takes about ten seconds and the gateway stays reachable. Without the screen, workshop mode ENFORCE --gateway hr-dev does the same.
  7. commandworkshop call --as hr-dev submit_leave_request E1001 15 → JSON-RPC error -32002. Policy blocks before the tool runs.
  8. fileInspect platform_sdk/platform_sdk/templates/agent_role.json: InvokeGateway on the project's gateways in its own environment only (the pattern hr-assistant-dev-gw*; it also matches hr-assistant-dev-gw-obo, though that door admits realm tokens, not IAM roles), no lambda:InvokeFunction and no bedrock:InvokeModel. This is a permissions inspection, not a call.
  9. commandworkshop obo: two hops now. Steps 1 and 2 of its output repeat module 2 (T0, then T1 by hand). Step 3 calls hrapi___get_leave_balance on hr-assistant-dev-gw-obo with Authorization: Bearer T1; the gateway exchanges T1 for T2 and calls the HR API, which answers with the tool's JSON. Step 4 reads the evidence from the HR API log: tool get_leave_balance: sub (same as T0), employee_id E1001, aud ['hr-tools-api'], azp hr-obo-gateway. Compare the tokens: the sub never changed, the audience changed at every door, azp names the client that asked.

The evidence line comes from the adapter in front of the HR tool, built from the claims API Gateway validated. It proves four things: the token reached the tool; it still names Alex (same sub as T0); it was addressed to this API alone (aud hr-tools-api); and the gateway asked for it (azp hr-obo-gateway). The log group /aws/lambda/agent-platform-hr-api is where production would look to learn who was really served; workshop obo prints a console link to it at the end of its output.

Remember. IAM controls gateway access; Cedar controls operations; targets control data. Observe policies, enforce them, then prove the deny with a real call. When the person matters, the tool learns who asked from a token addressed to it, never from an argument.

Glossary

Gateway
The controlled entry point agents use to reach tools.
MCP
Model Context Protocol: a common interface for agents to discover and call tools.
Target
A backend connected to a gateway, such as a Lambda function, API or knowledge base.
Lambda
AWS service that runs a tool's code on demand.
Knowledge base
Documents indexed for retrieval; here, managed HR policies in Amazon Bedrock.
Policy engine
Evaluates Cedar rules for tool access and arguments.
LOG_ONLY
Records policy decisions without blocking calls. Tools can still refuse requests.
Multi-hop
An agent calls another agent, which may call further gateways or tools.
Private target endpoint
Gateway-to-target access into a VPC through VPC Lattice. Separate from the agent-to-gateway PrivateLink path.
Quota
A service limit. Tool-call limits apply both per gateway and per account.
OpenAPI target
A target described by an OpenAPI document; each operation becomes a tool, and the gateway calls the HTTP API behind it.
JWT authorizer
A door that checks a token's signature, issuer, audience and expiry before a call passes. AgentCore Gateway has one for inbound calls; API Gateway has one in front of the HR API.
Outbound token exchange
Before calling a target, AgentCore Identity exchanges the caller's token for one addressed to that target (RFC 8693, decision 2.4).
OAuthUser
The policy engine's principal for a caller with a token rather than an IAM role: AgentCore::OAuthUser, the token's sub, which is the person.
