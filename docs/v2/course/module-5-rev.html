One door for every model Explain · 10 min

A model gateway sits between agents and models. It provides five controls:

  1. Access: approved model aliases.
  2. Rate: tokens and requests per minute.
  3. Spend: budgets and caps.
  4. Safety: a guardrail on every model call.
  5. Attribution: cost recorded per key.

Option A is a product category rather than one product. Self-hosted gateways such as LiteLLM, used here, or Portkey's open-source gateway run inside your VPC and keep model traffic on the private path of decision 1.2; hosted routers such as OpenRouter or Portkey's hosted service can reach Bedrock, but they do so from outside your account over the public internet, so they do not fit an endpoints-only network. Anthropic's Claude apps gateway is the same idea for developer tooling: it sits between developers' Claude Code clients and the model provider, and has no service-token flow for unattended workloads, so it is not a path for agents.

This workshop. LiteLLM runs on ECS Express Mode with RDS for keys and spend records. Its ten configured aliases (see MODEL_CATALOG.md in the repository), from three vendors (Anthropic, OpenAI and Amazon), inherit the baseline guardrail; the HR project's team may use two of them, claude-sonnet-5 and gpt-6-1-sol, and its Dev key one.

LiteLLM is a proxy server: it receives each model request and passes it on to Bedrock. Model gateway, LiteLLM and proxy therefore name one service. The proxy is private and has two access paths:

  • Agents in the VPC: reach its internal load balancer directly.
  • Control plane, CLI and laptop: use an IAM-authorised Lambda relay. Admin calls also require the master key.

Guardrail placement: at each alias, rather than per agent, account or tool policy. Every call names an alias, so agents inherit the filter. The browser cannot reach LiteLLM's private /ui; Governance shows its URL and credentials.

Production path. Use one gateway per environment, Multi-AZ, scoped admin keys and domain-specific guardrails.

This workshop. Spend has two enforced levels:

  • Project team: 5 USD / 7 days, plus project-wide rate limits.
  • Agent key: 1 USD / 7 days, per agent, environment and model.

At the cap, calls return BUDGET_EXCEEDED; admin can raise it in Keys. Caps follow agent keys, not users. Seven-day periods avoid a midnight UTC daily reset during the event.

Keep three numbers separate:

  1. Declared: a planning allocation in the blueprint.
  2. Measured: usage recorded in spend logs.
  3. Enforced: dollar caps and rate limits that block calls.

Production path. Alert before caps are reached. Add per-user enforcement with LiteLLM Enterprise where needed; AWS Budgets by tag provides alerts, not model-call caps.

Outage behaviour must be chosen and tested:

  • LiteLLM: default fail closed on database loss, except cached keys; allow_requests_on_db_unavailable changes this.
  • Claude apps gateway: developer-tool gateway; default fail open, with a fail-closed option.

The workshop uses LiteLLM's default. Database-outage behaviour is not tested here.

This workshop. All ten aliases map to us. profiles. Calls enter us-east-1 and may run elsewhere in the US geography. Other platform resources stay in one Region.

Routing follows three rules:

  • Platform choice: the alias map sets the route; agents choose aliases, not Regions.
  • Permission: a denied destination fails the request. An SCP does not narrow the route.
  • Fallback: preserve tool-call support and permitted processing Regions. A fallback cannot bypass a denial.

Production path. Define processing locations per data class. Use bedrock:InferenceProfileArn for SCP profile exceptions. An alias names a route; CloudTrail's inferenceRegion proves where processing occurred.

Capacity and resilience across accounts: LiteLLM fan-out (production pattern, not deployed)

Account quotas for model tokens and requests apply per account and Region. A platform that outgrows one account can give one LiteLLM alias several deployments, each calling Bedrock through a scoped role in a different model account, and let the router balance and fall back between them. It can add usable capacity and a second account-level failure domain once each account's quotas, model access and failure domains are validated; adding an account alone guarantees neither capacity nor resilience.

  • What it needs: cross-account trust for each invocation role, private access from the gateway, model access and quotas in every account, retry and fallback rules, and spend attributed back to the calling key.
  • What it does not do: it does not change where a request may be processed. Each deployment still uses its inference profile, so the geography rules above, IAM and the SCPs apply in every account. It does not guarantee failover when the shared Region or the model provider is degraded.
  • In this workshop: one account and one deployment per alias. The configuration has no router fallbacks, and the gateway's task role may invoke Bedrock only in its own account.

Platform complete. Hands-on 20 min

Make a key, cap it, approve the records, and the platform is complete

The proxy has run since module 1. This module adds its governed Dev key and approves the catalogue records. CLI proxy calls use the relay.

  1. recordSet the key cap in design-record.yaml.
  2. commandworkshop apply 5: it first prints the governance summary (the ten aliases, each with the hr-baseline guardrail, the policy engine, the gateways) and the project team's spend against its budget. It then creates the Dev key, capped as your module 5 input says and restricted to the model you chose in module 3 (model under module_3.inputs), and makes three calls with the raw key before putting it away: a normal question, where you read the answer, the token usage and the cost header x-litellm-response-cost; a question about suing a manager, which the guardrail stops with finish_reason=content_filter and the blocked message; and a call with the project's other allowed alias, gpt-6-1-sol, which the proxy refuses with HTTP 403 because the key may use one model only. Only then does it store the key in the AgentCore Identity token vault (this creates the key's API key credential provider), register that provider with the platform and adopt the key, which now appears in the project's Keys tab, and wait for the first spend to be recorded. On a re-run the key and provider already exist, so the command reuses them and skips the three calls.
  3. commandworkshop cap --dev low: as the Platform admin it lowers the Dev key's cap to half of what the key has spent so far (never more than 0.01 USD; 0.01 when no spend is recorded yet) and makes one more call through the proxy, which refuses it before any model runs: OK BUDGET_EXCEEDED, gracefully: HTTP 422, Budget has been exceeded! Key=… Current cost: …, Max budget: …. The text after the comma is LiteLLM's own wording (its error type is the lower-case budget_exceeded); BUDGET_EXCEEDED is the platform's code for the same refusal, which workshop ask prints and the Playground shows as its "Spending cap reached" alert from module 6 on. If the call still passes, the spend the command read had not been written yet (the proxy writes spend in batches every 10 seconds), so the cap it set is still above the real spend: run the command once more. Then workshop cap --dev restore writes your record's cap back before module 6.
  4. screenSwitch to Platform admin: every persona can read the catalogue, but only the admin may change a record's status. In Catalogue, filter on Pending approval and approve the three records that workshop apply 4 submitted: hr-assistant-tools (the MCP server of the HR Dev gateway), kb-hr-policies (the HR policy knowledge base) and model-claude-sonnet-5 (the model alias named in your record). Approved records become searchable. If the screen is unavailable, workshop approve catalogue approves every pending record from the command line.
  5. commandworkshop inventory: verify the shared platform resources.

Three results to notice. The cost header prices one call, and that spend is what the Keys tab and the caps count. The guardrail answer comes back as a normal completion with finish_reason=content_filter, so an agent can handle it gracefully instead of failing. The wrong alias is refused before any model runs, because access is a property of the key, not of the caller.

Dashboard spend updates about 10–15 seconds after a call.

Remember. The tool gateway controls actions. The model gateway controls model access, safety, rate, spend and routing.

Glossary

Model gateway
Controls model access, rates, spend and guardrails. Here it is the LiteLLM proxy.
Proxy
The LiteLLM server that is this workshop's model gateway; model gateway, LiteLLM and proxy name one service.
Alias
Stable model name, such as claude-sonnet-5, mapped to a Bedrock model or inference profile.
Team
A project's allowed models, rate limits and budget in LiteLLM.
Virtual key
Model-gateway credential per agent, environment and model, with its own cap.
Cap
Enforced dollar limit that resets each period.
Throttling
Limits on tokens or requests per minute.
Inference profile
Bedrock routing object: geographic profiles route within a geography; global profiles route more widely. Application profiles support cost tags.
Source, destination Region
Where a request enters, and where the model processes it. Cross-Region inference can make them differ.
Fail open, fail closed
Allow calls or stop them when a control cannot be checked.
Agent Registry
AWS catalogue with record states, approvals and change events.
