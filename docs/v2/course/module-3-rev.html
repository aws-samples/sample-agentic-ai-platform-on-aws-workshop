The platform as an operating model Explain · 10 min

The control plane has four parts: UI, API, state table and worker. Together they hold three shared things:

  1. Rules: policies, guardrails and caps.
  2. Approved lists: models, tools and knowledge.
  3. Ownership records: domains, projects and releases.

For every shared layer, record two boundaries:

  • Enforcement: the permission or trusted filter that separates tenants. Namespaces, UI filters and session labels alone do not.
  • Failure and ownership: outages, noisy tenants, revocation and data cleanup. Security isolation does not guarantee capacity isolation.

3.2Governance: which rule lives at which level?

OptionProsConsChoose when
Everything at platform levelone team, one rulebooka bottleneck; rules far from the businessone domain, a few agents
Layered: the platform sets guardrails, domains approve, projects own the rest, with a gate at every promotioneach rule sits with the people who know; evidence at every levelthree levels and a gate to design; rollout needs careseveral domains sharing one platform
Each project governs itselffastest for teamsno shared rules; every team reinvents themnever for shared tools or models

This workshop. Governance has three levels and one gate. A level is defined by who owns its rules:

  1. Platform: models, guardrail, policy engine, catalogue approval and default caps.
  2. Domain: release approval.
  3. Project: the agent blueprint and thresholds, within admin-set allow-lists, roles, keys and budgets.

Gate: evaluation before Prod, then promotion and rollback (module 6). The gate is not a fourth level, because it owns no rules of its own. At every promotion, here from Dev to Prod, it runs the project's release through the domain's approval. Today a worker runs it; in production a CI/CD pipeline does, with its checks in front of the platform API.

SCPs are discussed, not built. The event account cannot administer its AWS Organization. A security-team SCP would add a permission ceiling; IAM must still grant access.

Production path. Add organization SCPs and gateway resource policies; do not assume RCP coverage for these services. Document effective rules and exceptions. Give domains their own gateways and policies.

This workshop. Module 4 creates one AWS Agent Registry. Admin approves records; every persona reads them through the platform. Decision 5.3 explains the service choice.

Keep three permissions separate:

  1. Discover: one fixed type per registry: IAM or corporate JWT. We use IAM through the platform API. Whoever may search or list sees every approved record. The record-owner condition keys apply when a named record is read or changed, not to search and list. When a registry is shared across accounts (option B), only a RAM share that leaves out those two actions keeps other accounts' records out of view.
  2. Publish and approve: always IAM.
  3. Invoke: the endpoint's permissions apply. Discovery and an approval label grant no execution access.

Production path. Use an organization-scoped IAM registry with auto-detection and read-only or consumer RAM sharing. IDE builders need a separate JWT registry or mediated view. Make domain-owner approval part of the release gate (3.2).

Hands-on 20 min

Onboard a domain and a project
  1. recordSet the domain, project, owner, models, model and budget in design-record.yaml, then run workshop record: it prints the effective inputs with the defaults filled in for anything you left out, or the list of problems, and needs no AWS access. Every workshop command runs the same check first, so a bad value stops apply 3 before anything is built: the domain and project ids must be kebab-case (hr-assistant), model must be one of models, the budget numbers must be positive and its period a duration such as 7d, and the Finance names finance-ops and invoice-helper are reserved.
  2. commandworkshop apply 3: create two domains and two projects. Each project gets four roles (a pair per environment) and one model budget. After its title line and the path of your record, the command prints four sections. domains and projects report what it created; run it again and the same lines say exists (or existed: aligned it if you changed the models in your record), because every apply adopts what is already there. what the platform stamped for the HR project lists the model-gateway team with its models and budget, then the agent role and the gateway role of each environment. the boundary, proven from the agent role first prints who may assume the Dev agent role (the AgentCore service, and the account root so that this command can), then assumes it and calls the Finance and the HR tool Lambda directly. Both calls must end in AccessDeniedException, followed by an OK line: those two denials are the proof this module is after. The project's agent reaches tools only through its own gateway, which module 4 creates. The run takes well under a minute; a brand-new role can make it wait up to a minute more for IAM. Expected lines below.
  3. screenDomains and projects: check the project's caps, models and roles.
  4. screenIn IAM, open the two Dev roles the platform stamped: agent-platform-proj-hr-assistant-dev-agent (the command's last look line prints its console link) and agent-platform-proj-hr-assistant-dev-gateway. The agent role has no bedrock:InvokeModel and no lambda:InvokeFunction; its only path to a tool is bedrock-agentcore:InvokeGateway on gateways named hr-assistant-dev-gw*. The gateway role is the one allowed to invoke the HR tools Lambda and query the knowledge base. Both trust the account root: the first shortcut from decision 3.1. The command already proved the Lambda half: both direct calls from the agent role ended in AccessDeniedException.

The two AccessDeniedException lines are not an error. The agent role holds no permission to invoke any Lambda, so the tools are out of its reach until module 4 puts the project's gateway in front of them, and the OK line confirms that both calls were refused. The state file .workshop/state/hr-assistant.json is where every apply records what it created, so that later modules and the other workshop commands can find it. The two look lines are the screens of the next two steps. If the last section instead prints WARN could not inspect the agent role ... IAM may still be propagating, the new role was not yet visible when the command tried to assume it; run the command again, it is safe to repeat.

Remember. Put each rule with its owner and an enforcement point. A label names a scope; a permission or trusted filter enforces it.

Glossary

Control plane
The platform's UI, API, state table and worker.
Tenant
A business unit whose data and actions must stay separate. Here, a domain; controls are scoped to its projects.
Governance
Rules, their owners, where they are enforced and who may change them.
Guardrail
A safety filter applied to model requests and responses.
Policy engine
Evaluates Cedar rules for tool calls.
Catalogue
Records of tools, knowledge and models, held in AWS Agent Registry.
Discover, publish, invoke
Find a record; create or approve it; call its endpoint. The endpoint controls invocation.
SCP
An AWS Organizations permission ceiling for member accounts. It grants no permissions; IAM must still allow the action.
Separation of duties
Different people build and approve a release.
