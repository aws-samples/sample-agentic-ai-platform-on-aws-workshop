Why it matters to me?

An enterprise agentic AI platform is the shared technology, controls and operating practices that let teams build, deploy and run AI agents consistently.

By consistency we mean:

  • One way to reach approved models and tools
  • One place to see usage and cost
  • One release standard
  • One set of safety controls

Without it every team rebuilds infrastructure, quality drifts, access control and governance gets lost.

Learning objectives

By the end of the day you will be able to:

  1. Explain what an agentic AI platform is, why an enterprise needs one, and which capabilities make it up.
  2. Assemble a functional platform using Amazon Bedrock AgentCore building blocks and explain each one's role, integration points and design trade-offs.
  3. Configure platform shared governance and establish boundaries between Business domains and Projects.
  4. Bootstrap an agent project from a configuration-driven Blueprint that references governed resources.
  5. Run an agent through full AgentOps lifecycle covering build > deployment > quality gate > release approval > promotion > monitoring and a feedback loop.

What you'll build

① Platform

The platform separates a control plane from workloads (data plane).

  • The control plane owns what is shared, long-lived or governance-bearing, plus the lifecycle machinery:
    • Platform UI, APIs and state
    • Business domains, projects and personas (user groups)
    • Permissions
    • Catalogue, policy engine, baseline guardrail
    • Model gateway (with spending cap)
    • Observability
    • Release and approval workflow
  • A workload (a project inside a business domain) owns what encodes its use case:
    • Gateway and tools
    • Memory
    • Agent definition
    • Evaluation and quality gates

    Project resources exist once per environment: Dev and Prod. For this workshop we use one AWS account.

In the workshop you will play three personas on the platform:

③ Workload (HR Assistant)

You will build an HR Assistant AI Agent for AnyCompany HR on this platform.
The agent itself is an AgentCore Harness, a configuration-driven managed agent you declare using platform's Blueprints rather than hand coding from scratch.
This ensures quality controlled development of a production-grade, versioned agent.

Teams that need custom orchestration can export a harness to Strands Agents or LangGraph code with workshop export (written to exports/) and deploy it to AgentCore Runtime.
This workshop shows the export as an optional step; the deployment pipeline is discussed, not built.

② Request flow

Step-by-step explanation
  1. User invokes the AgentCore Harness endpoint with a session id. Agent runs the session in its own microVM.
  2. The harness fetches its virtual key from the AgentCore Identity token vault and calls LiteLLM. LiteLLM enforces model allow-list, rate limits and budgets for the project (via virtual key), applies the Bedrock guardrail attached to the model alias, calls Amazon Bedrock, and records usage and cost.
  3. If the model asks for a tool, the harness calls the project AgentCore Gateway. The Policy engine evaluates the Cedar policies for the harness's execution role, the tool and its arguments, then the gateway invokes the Lambda tool or the knowledge-base connector.
  4. Memory events are written for the session. A long-term strategies extract summaries and preferences asynchronously.
  5. The answer streams back with usage metadata. Spans and metrics land in CloudWatch. The spend row lands in LiteLLM; Online evaluation scores the session with a few minutes delay asynchronously.
All model requests goes through the Model Gateway (LiteLLM). All tool access goes through the AgentCore Gateway.
These two choke points enforces who may use what, how much, and under which rules.

③ Release flow

Step-by-step explanation
  1. workshop apply 6 (or the Releases screen) stores blueprint version n; the worker creates the immutable Harness version and deploys it to the Dev harness.
  2. The evaluation run invokes the Dev endpoint for every scenario, waits for telemetry, and scores each scenario with built-in evaluators. The worker runs it for a release created on the Releases screen (or with Run evaluation); workshop apply 6 runs it itself and posts self-reported scores.
  3. The platform compares scores with the thresholds in the blueprint and marks the release BLOCKED or PENDING_APPROVAL.
  4. The Domain approver reviews the evidence in the UI and approves.
  5. The worker runs promotion from the UI or API: it renders the same blueprint for Prod (Prod gateway, memory and key, creating the Prod key when missing), updates the Prod harness, repoints the live endpoint to the new immutable version, and ensures online evaluation is monitoring it.

② Platform UI: Configure the control plane

As a Platform admin, Agent developer and Domain approver, you will use the pre-built Platform UI and API to complete the following:

Platform UI What you'll do
Overview Watch invocations, errors, latency, tokens and spend against caps, policy allow/deny counts and quality scores, filtered by domain, project, agent and environment
Domains and projects Create a business domain and a project; set the project's budget, reset period, rate limits and approved models (which creates the LiteLLM team and project roles); see each agent's key, spend and cap; suspend or raise
Catalogue Browse, search and approve or reject Agent Registry records for tools, knowledge bases and models
Governance See approved models, the baseline guardrail, the policy engine and its policies; switch a gateway between log-only and enforce
Releases Review evaluation results against thresholds, approve or reject a release candidate, promote the approved version to Prod, see version history
Playground Chat with the Dev or Prod agent, see the tools it used and the tokens it consumed, and rate the answer
The Platform control-plane backend (API Gateway, Lambda API and worker, DynamoDB) owns the lifecycle machinery:
  1. It stamps LiteLLM teams and IAM roles at project creation, adopts the Dev key and creates the Prod key at promotion; raw keys live only in AgentCore Identity
  2. Its worker renders blueprints, deploys Dev versions, runs the dataset for releases created on the Releases screen, applies evaluation thresholds, records approvals and performs promotions
You configure the control plane; you do not develop it.

④ Build the agent: Experience the full lifecycle

Finally you will use the platform to build a simple HR assistant agent (workload) and run through the full lifecycle from blueprint to production.

Scenario
AnyCompany's People Operations domain (people-ops) runs an HR assistant for employees.

  • It checks leave balances
  • It answers HR policy questions from the knowledge base with citations
  • It submits leave requests
  • It provides information about public holidays

In addition, there is a Finance Operations domain (finance-ops) with a project invoice-helper, four IAM roles and a budget, but no agent. It proves the boundary: module 3 with an AccessDeniedException, module 4 with workshop call --as finance-dev (HTTP 403 from IAM, before any policy). The policy engine is proven by the HR agent itself: once the HR Dev gateway is in ENFORCE, its own 15-day leave request is denied with JSON-RPC error -32002.

Prepared assets. Synthetic employee, leave and invoice tables; five Lambda tools (four HR, one Finance) and an HR API; five HR policy documents with department metadata in a managed knowledge base; a baseline guardrail; a blueprint template; an evaluation dataset of about ten scenarios; a short risk register.

The blueprint is a small YAML specification. The platform resolves its references against the approved catalogue and settings for a given environment and renders the harness configuration: 

apiVersion: platform/v1
kind: AgentBlueprint
metadata: {domain: people-ops, project: hr-assistant, version: 1}
spec:
  model: {ref: model/claude-sonnet-5-5}                  # approved alias in the model gateway (baseline guardrail included)
  systemPrompt: {file: prompts/hr-assistant-v1.md}       # relative to this file; the API stores the resolved text
  tools: [{ref: tool/hr-core}]                           # the environment's gateway: hrtools___* Lambda tools + hrkb___Retrieve
  knowledge: [{ref: kb/hr-policies}]                     # knowledge-base connector target on the same gateway (department == HR)
  memory: {strategies: [SUMMARIZATION, USER_PREFERENCE]} # the environment's registered memory
  limits: {maxIterations: 30, maxTokens: 4000, timeoutSeconds: 120}
  budget: {perModelCap: 1.00, resetPeriod: 7d}           # virtual key cap for this agent, environment and model (USD; 7d avoids a UTC-midnight reset mid-event)
  evaluation:
    dataset: evaluation/hr-assistant.json                # relative to scenario/ (also uploaded to the dataset bucket)
    thresholds: {Correctness: 0.8, GoalSuccessRate: 0.9, TrajectoryInOrderMatch: 0.9, Harmfulness: 0.0}

Lifecycle you run
You will configure a project, deploy to Dev, run tests and evaluations, review results and approve, promote to Prod.

Dev and Prod are lifecycle labels on platform. Each has its own Gateway, Memory, Harness and Key.

For each deployed agent, you will monitor, improve and re-evaluate the deployed agent to mimic real-life experiences. The evaluation (quality gate) covers:

  • Task success
  • Response quality
  • Tool use
  • Selected safety cases with documented pass/fail thresholds

Version 1 of the agent system prompt deliberately omits the instruction to use the policy search tool, so that the policy question scenarios fail and the release is blocked.
Version 2 passes and waits for the Domain approver (PENDING_APPROVAL).
The spending cap demo is module 5: workshop cap --dev low makes the Dev key fail with BUDGET_EXCEEDED (the Playground shows "Spending cap reached"); workshop cap --dev restore lifts it again before module 6.

At the end, Promotion records the approved version and repoints the Prod endpoint. A risk register anchors the responsible-AI and approval discussion.

Out of scope

This is a functional learning MVP that demonstrates and teaches enterprise platform practices.

Not covered

  1. Production hardening (Multi-AZ database and model gateway, scoped endpoint policies, AWS WAF, custom domains and certificates)
  2. A SaaS identity provider tenant or federation (the workshop builds Keycloak and the RFC 8693 on-behalf-of chain in modules 2, 4 and 6)
  3. Multi-account landing zones
  4. External integrations
  5. LiteLLM Enterprise features (per-model budgets on a shared key, tags, aggregated reports)
  6. CI/CD pipelines for agents

Key design decisions and trade-offs

  • Configuration first, code when needed. Agents are AgentCore Harness resources rendered from a blueprint. No containers or build pipelines in the workshop; workshop export to Strands Agents or LangGraph code remains available for teams that need custom orchestration.
  • One account, two environments. Dev and Prod resources are separate but live in one account; promotion pins an approved immutable version to the Prod endpoint. Multi-account topologies are covered in the presentation as the production extension.
  • Two choke points for governance. Tool access is governed at the AgentCore Gateway with Cedar policies (what, with which arguments, under which conditions). Model access is governed at the model gateway with teams, keys, allow-lists and caps (which models, how much, how fast).
  • Open-source LiteLLM for spending caps. Budgets in dollars with automatic resets are enforced per project (team) and per agent, environment and model (one virtual key each). Keys never appear in agent configuration; they live in the AgentCore Identity token vault.
  • Guardrails where they cover everything. The baseline Bedrock guardrail is attached to the approved model aliases in the model gateway, so every agent inherits it with a graceful blocked reply; gateway policies can add guardrail checks on tool traffic.
  • Evaluation before and after release. A dataset run with built-in evaluators gates promotion; online evaluation watches Prod continuously; both feed the same dashboard as usage and cost.
  • Everything visible in one place. AgentCore metrics, policy decisions, evaluation scores and LiteLLM spend are read by the platform dashboard; no log parsing.
  • Identity with one real chain. Cognito for the three personas, IAM SigV4 between the harness, gateway and tools, API keys in the token vault for the model gateway. The corporate IdP (Keycloak) and the on-behalf-of token exchange (RFC 8693) are built in modules 2, 4 and 6; a SaaS IdP tenant is not.

Rebuild it at your own pace

Prerequisites

  • An AWS account with administrator access in us-east-1 and Amazon Bedrock model access for Anthropic Claude and Amazon Nova (a one-time use-case form for Anthropic models).
  • A terminal (PowerShell on Windows), Git, uv, Node.js 20 or later (for the CDK CLI) and an editor. No Docker, no AWS CLI; the AWS CLI is only needed to create a named profile for your own account.

Steps

git clone <repository>
cd workshop-agentic-ai-platform
uv sync && npm install                    # Python environment and the CDK CLI: 2-5 minutes
source .venv/bin/activate                 # Windows: .venv\Scripts\Activate.ps1
export AWS_PROFILE=<your profile>         # or paste the event credentials
export AWS_DEFAULT_REGION=us-east-1
workshop deploy pre-day                   # control plane and sample data: about 12 minutes (or scripts/deploy.sh --pre-day)
workshop status                           # eight stacks: four CREATE_COMPLETE, four not deployed
workshop apply 1                          # landing zone: about 20 minutes
workshop apply 2                          # ... then 3 to 7, one module at a time
workshop cleanup                          # at the end; workshop cleanup --stacks removes the stacks

Approximate running cost

The landing zone (private endpoints, the model gateway on ECS Express Mode with its database) costs about 0.28 USD per hour while it runs; the Keycloak IdP adds about 0.08 USD per hour. Agent sessions, evaluations, memory and the knowledge base add cents per module. workshop cleanup removes what the modules created; workshop cleanup --stacks then removes the stacks.

Glossary

Term Meaning
Harness An AgentCore resource that runs a managed agent loop from configuration: model, prompt, tools, memory, limits and hooks, with immutable versions and named endpoints
Blueprint The platform's YAML specification of an agent; the renderer resolves references against the catalogue and settings for an environment
Gateway target A tool source attached to an AgentCore Gateway: Lambda function, API, MCP server or connector such as the managed knowledge base
Policy engine A set of Cedar policies attached to a gateway and evaluated on every tool listing and call, in log-only or enforce mode
Team and virtual key LiteLLM objects: a team holds a project's budget, limits and allowed models; a virtual key identifies one agent, environment and model with its own cap
Budget duration The period after which a LiteLLM budget resets, for example one day or one month
Guarded model alias A model name in the model gateway that carries a Bedrock guardrail, so every call through it is checked on input and output
Credential provider An AgentCore Identity object holding an API key or OAuth client in the token vault; the harness references it by ARN
Endpoint and version A harness version is immutable; an endpoint such as live is a named pointer that promotion moves from one version to the next
Evaluator A scoring function in AgentCore Evaluations, for example Correctness, GoalSuccessRate, TrajectoryInOrderMatch or Harmfulness
Online evaluation Continuous sampling and scoring of production sessions from CloudWatch spans
Transaction Search The CloudWatch account setting that stores and indexes spans so AgentCore Observability and Evaluations can use them
Persona A role an attendee plays: Platform admin, Agent developer or Domain approver, mapped to the Cognito groups platform-admins, agent-developers and approvers; Switch persona changes roles
Design record design-record.yaml at the repository root: your inputs and one decision per section (workshop or my_call), checked with workshop record
workshop command The course CLI: workshop apply N builds module N from the design record; also record, obo, call, cap, ask, mode, approve, promote, inventory, traffic, scores, export, deploy, status and cleanup
Landing zone The Network, SharedServices and ModelGateway stacks deployed by workshop apply 1: one VPC with private endpoints, the baseline guardrail and the model gateway
Worker The control plane's background Lambda: renders blueprints, creates Harness versions, deploys Dev versions, runs the dataset for releases created on the Releases screen and promotes
Release states BLOCKED, PENDING_APPROVAL, APPROVED, PROMOTED: the thresholds decide the first two, the Domain approver the rest
On-behalf-of token exchange RFC 8693: the employee's Keycloak token (T0) is exchanged for an agent token (T1) and a tool token (T2), so the tool sees who asked; token passthrough is forbidden
Corporate IdP (Keycloak) Self-hosted Keycloak in the AgentPlatform-Idp stack, realm anycompany, deployed by workshop apply 2; where employees such as Alex Rivera sign in
State file .workshop/state/<project>.json (git-ignored): the ids the workshop commands created, read by later modules and removed by cleanup
